# long-task-guidance

面向 agent 的长任务执行与防漂移规范（完整规范见 [SKILL.zh.md](SKILL.zh.md)）：将目标、规格、进度与决策外置为文件，对抗上下文压缩与目标漂移，使任务可在任意中断点无损恢复。

## 最佳使用方式

**不需要将本 skill 长期挂载到 coding agent。** 推荐用法：

1. 启动任务前，将 `SKILL.md` 复制到目标项目中；
2. 让 agent 读取该文件，按其中规定的流程执行任务；
3. agent 会在项目内按规范生成并持续维护全套任务文档。

## 适合场景

- **长任务**：跨多次会话、多阶段持续推进的复杂任务。文件即记忆，上下文被压缩或对话中断后，凭 `STATE.md` 与规格文件即可无损续作。
- **短任务（人机协同维护文档）**：任务不大时同样可用本规范约束 agent 落盘文档——人通过审查文件了解与干预进度，而非翻聊天记录；文档即协作界面。
- **vibecoding**：自然语言驱动写码时，「规格先行 + 带序号验收清单」给感觉一个客观锚点；增量修改台账让需求变动可回放，防止越写越偏，交付包括功能、链路、原理，方便验收。

## 规定的工作流

每个工作单元（一个目录 = 一个工作单元）按以下顺序推进：

| # | 步骤     | 要点                       |
| - | ------ | ------------------------ |
| 1 | 调研先行   | 动手前检索领域最新实践，避免过时直觉       |
| 2 | 规格先行   | 规格未定，不进入实现               |
| 3 | 树形组织   | 总体目录 → 功能模块 → 子功能模块，逐层细化 |
| 4 | TDD 实现 | 先写测试再写实现，测试通过才算完成        |
| 5 | 串行完成   | 彻底完成当前单元再进入下一单元（含计划清零）   |
| 6 | 增量记录   | 需求/规格改动必须登记增量，禁止静默覆盖     |
| 7 | 架构纪律   | 禁止补丁叠补丁，出现堆积时回溯重构        |
| 8 | 交付     | 每单元产出功能文档 + 原理文档         |

配套机制：

- **抗压缩重读协议**：新单元开始前、子任务完成后、上下文被压缩后，必须重读状态与规格文件再推进，禁止凭残留记忆干活。
- **提交与检查点**：每完成一个工作单元提交一次代码，提交信息关联文档路径。

## agent 的交付物

```text
<任务文档根目录>/
├── STATE.md                         # 顶层状态入口（唯一）
├── 环境.md                          # 用户填写的环境说明（禁止入 git）
└── 00-总体-<项目名>/
    ├── 理论调研.md / 需求文档.md / 架构设计.md
    ├── 开发计划与进度.md / 增量修改文档.md
    ├── <功能模块>/
    │   ├── 需求文档.md / 规格文档.md（含带序号验收清单）
    │   ├── 开发计划与进度.md / 增量修改文档.md
    │   └── <子功能模块>/             # 结构同上，粒度更细
    └── 交付/<功能模块>/
        ├── 功能文档.md               # 做什么、怎么用
        └── 原理文档.md             # 依据什么原理、整体链路
```

| 层级           | 交付文档                      |
| ------------ | ------------------------- |
| 顶层           | `STATE.md`、`环境.md`        |
| 总体目录         | 理论调研、需求、架构设计、开发计划与进度、增量修改 |
| 功能模块 / 子功能模块 | 需求、规格、开发计划与进度、增量修改        |
| 交付层          | 功能文档、原理文档                 |

其中**开发计划与进度**强制为表格格式（任务表 + 子任务表），含状态列（未开始 / 进行中 / 已完成 / 受阻），并通过验收清单序号与规格文档关联；跨模块与集成阶段任务只登记在总体计划中。
